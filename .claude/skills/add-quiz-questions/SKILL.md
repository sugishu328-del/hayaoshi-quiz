# hayaoshi-quiz 問題バンクの追加

A/B/C各難易度に新しい問題をまとめて追加する際の、確立済みのワークフロー。2026-08-28に856→1490→1789問の2回にわたって実行し、プロンプトを改善しながら磨き上げた([[project_question_bank_1789]]参照)。

## 全体の流れ

1. 現時点の全問題文(重複確認用)をエクスポートする
2. 難易度ごとに1体、計3体のサブエージェントを並行起動し、それぞれ指定数の問題をリサーチ付きで作成させる
3. 各サブエージェントの成果物(下書きJSON)を検証・マージする
4. `questions.json`に反映し、実プレイで動作確認する
5. コミット前にユーザーに確認する

## 手順1: 重複確認用データの準備

```js
const q = require('./questions.json');
const fs = require('fs');
const out = { A: q.A.map(x=>x.question), B: q.B.map(x=>x.question), C: q.C.map(x=>x.question) };
fs.writeFileSync('<scratchpad>/existing_questions.json', JSON.stringify(out, null, 1));
```
スクラッチパッド(セッションごとのテンポラリフォルダ)に保存する。

## 手順2: サブエージェントを起動

`Agent`ツールで `subagent_type: general-purpose`, `model: opus`(リサーチの質を優先), `run_in_background: true` を指定し、以下の内容を含むプロンプトで起動する。

**A/B/C全難易度に追加する場合**: 難易度ごとに1体、計3体を並行起動する(各エージェントが別の難易度という別々の題材空間を担当するため、並行させても内容が被りにくい)。

**特定の難易度だけに追加する場合(例: 「Aだけ300問」)**: **1体にまとめて依頼する**(並行させない)。同じ1つの難易度を複数体に並行で書かせると、各エージェントが独立に「その難易度でまず思いつく定番トピック」(首都・有名な公式・著名な受賞者など)に偏って収束し、相互の重複率が極端に高くなる(2026-10-05実績: 200問ずつ2体並行→相互重複27問=約13.5%。A/B/C分担時の相互重複率1〜9%と比べて明らかに高い、[[project_question_bank_2393]]参照)。件数が多くスピードのために並行させたい場合は、手順3のマージ時に「同一answerの組を全て目視で同一事実か判定する」突き合わせ作業が追加で必要になることを見込んでおく。

**プロンプトに必ず含める要素**:
- 難易度の基準(A=むずかしい/専門知識、B=ふつう/学校常識、C=かんたん/誰でも分かる)
- スキーマ({question, answer, input, distractors:[{name,input}]}、distractorsはちょうど3個)
- 絶対に守るルール:
  1. 事実誤りは絶対に避ける。数字・年代・「最も〜」系はWebSearchで裏取りする
  2. 答えの文字列が問題文にそのまま含まれてはいけない(答え漏れ、[[feedback_answer_leak_in_question]])
  3. 「AとBのうちどちらでしょう」形式は使わない(同上)
  4. answerにカッコ書きを含めない
  5. distractorのinputは正解のinputと完全一致しない
  6. distractor同士のinputも完全一致しない
  7. 4択の頭文字が偶然揃うのは問題ない(無理に散らさない、[[feedback_distractor_reading_collision]])
  8. 既存問題一覧(手順1のファイル)と重複しない、自分が作る分同士でも重複しない
  9. **答えやdistractorにローマ字の略称・記号・数字が含まれる場合、inputはその表記のまま使う(カタカナの音読みに分解しない)**。例: NaOH→"NaOH"(○)/"エヌエーオーエイチ"(✕)、O型→"Oがた"(○、漢字部分だけひらがな読みにする)。[[feedback_latin_abbreviation_input]] 参照。このルールをプロンプトに含めるだけで、事後の修正件数が44件→1件に激減した実績あり。
  10. **答えやdistractorにカタカナ表記の部分(外来語・外国の人名地名など)が含まれる場合、inputでもそのままカタカナ表記を保つ(ひらがなに変換しない)**。例: "チャイコフスキー"→input:"チャイコフスキー"(○)/"ちゃいこふすきー"(✕)。「カタカナ+漢字」混在の場合は、カタカナ部分はそのまま残し漢字部分だけ読みをひらがな化する。例: "キング牧師"→input:"キングぼくし"(○)/"きんぐぼくし"(✕)。「・」(中黒)区切りの人名は中黒を省いて連結してよい(例: "レオナルド・ダ・ヴィンチ"→"レオナルドダヴィンチ")。2026-10-04に既存バンクで173件この不具合が見つかり一括修正した実績がある([[project_question_bank_2393]]参照)。
  11. **言い換えでも答えが分かる問題を作らない**。問題文に答えそのもの・答えの核となる語・答えを一意に示す単位や別名が含まれるものは不可(答え漏れ、[[feedback_answer_leak_in_question]])。単に答えの一部が一般語として出てくるだけなら可。作成後、各問題を「問題文だけ読んで答えが当たるか」で自己確認する。
  12. **難易度を自己判定する**。A=専門知識が必要、B=学校で習う常識、C=誰でも分かる。作成時に迷う問題は、より該当する難易度で作るか、作らない。
  13. **問題文自体がカテゴリ(政策・条約・事件・戦争・革命・運動・協定・会議・同盟・制度・効果・現象・改革・帝国・宣言・法則など)を明示している場合、inputはそのカテゴリ語を省略してよい**。例: 「どういう政策でしょう？」という問題で答えが「ニューディール政策」なら、input は "ニューディール政策"(読み含め全部)ではなく "ニューディール" でよい。同様に「ベルサイユ条約」→"ベルサイユ"、「パリ協定」→"パリ"。カテゴリ語は問題文で既に与えられており、プレイヤーがそれを改めて1文字ずつ選ぶのは冗長なため。**「〜の法則」「〜の改革」のように助詞「の」でカテゴリ語とつながる場合は、カテゴリ語だけでなく末尾の「の」も削る**(例: 「オームの法則」→input "オーム"。"オームの" のように助詞で終わる形は不自然なため不可)。「フレミングの左手の法則」のように名前とカテゴリ語の間に別の語句がある場合は、末尾の「法則」とその直前の「の」だけを削り、間の「の」は残す(→"フレミングのひだりて")。**ただしinputを短くした結果、同じ問題のdistractorのinputと一致してしまう場合は短縮しない**(正誤判定が曖昧になるため)。2026-10-08に既存バンクで204件この短縮を一括適用し、さらに末尾に「の」が残っていた41件を追加修正した実績がある([[project_question_bank_2393]]参照)。
  14. **「何年」「何人」「何個」「何本」「何度」「何%」のように問題文が単位を明示している数値の答えも、inputは数字だけでよい**(ルール13と同じ考え方)。例: 「西暦何年でしょう？」で答えが「1948年」なら input は "1948ねん" ではなく "1948"。「何人でしょう？」で答えが「23人」なら "23にん" ではなく "23"。問題文に「約」「およそ」とある場合、答えの先頭の「約」もinputでは省略する(例: "約109倍"→input "109")。2026-10-08に既存バンクで68件修正した実績がある。
  15. **「何月何日でしょう」のような複合的な日付を答えさせる問題は作らない**。月と日の2つを同時に文字選択させることになり分かりにくい、とユーザー判断で2026-10-08に既存の4件(B232/B2816/C153/C182)を削除した。西暦年や単一の月・日を問うだけの問題(ルール14)は問題ない。
  16. **答えに本当に通用する別解(2つとも正式な呼び方として使われる表記)がある場合、inputはその共通部分までで正解にする**。ルール13は「問題文が既にカテゴリ語を言っているから省略してよい」という冗長性の話だが、このルールは別物:「〜力」のように外来語の人名・名称に直接「力」が付く物理用語は、本来「○○力」（助詞なし）が正式名称であることが多く、「○○の力」という言い方も並行して通用する(例: 「コリオリの力」と「コリオリ力」は両方とも正しい呼び方)。この場合、answerの表記はどちらか一方で構わないが、inputは両方に共通する部分(例: "コリオリ")までにして、「の力」まで入力しないと正解にならない、という事態を避ける。2026-10-09に既存バンクでこのパターンを全文検索し、該当は「コリオリの力」(A457)の1件のみと確認・修正した。新規作成時も、外来語+「力」の答えを作る際はこの観点を自己チェックする。
  17. **共通の接頭辞に切り詰める方法(ルール13/14/16)では吸収できない別解(読み方自体が途中から分岐する/文字数が揃わない)は、inputを配列にして両方登録する**(2026-10-09追加、room.jsのanswerCandidates分岐判定に対応)。例: 「日本」は「にほん」「にっぽん」どちらも正式な読みなので `input: ["にほん", "にっぽん"]` とする。これは「ほん」と「っぽん」で全く噛み合わないため、ルール16のような接頭辞切り詰めでは対応できない。**配列化する前に必ず`node scripts/validate-questions.js`を走らせ、(a)どの候補も同じ問題のdistractorのinputと衝突しない、(b)候補同士が完全一致または互いの接頭辞になっていない、の2点を確認する**(いずれかに該当すると分岐判定が壊れるか正誤判定が曖昧になるため、バリデータが自動検出してエラーにする)。また**「ヴ」を含む答えは、バ行表記(ヴァ→バ/ヴィ→ビ/ヴ→ブ/ヴェ→ベ/ヴォ→ボ)も日常的に広く通用するため、原則input配列に両方入れる**(例: 「ベートーヴェン」→`input: ["ベートーヴェン", "ベートーベン"]`)。2026-10-09に既存バンクで「ヴ」を含む109件を一括でこの形に変換した実績がある。
- ジャンルの幅(地理・歴史・理科・スポーツ・エンタメ・語学・数学・時事など)を指定し、偏りを防ぐ
- 出力先(スクラッチパッドの`new_A2.json`等、難易度ごとに別ファイル)を明示し、「questions.json本体は直接編集しない」ことを明記する
- 完了時に、作成数と不安が残るトピックを200〜300字で報告するよう指示する

## 手順3: 検証とマージ

各下書きファイルができたら:

1. **まず各下書き単体で検証**: `{A:[],B:[],C:draft}`のように空配列でラップして`node scripts/validate-questions.js <一時ファイル>`にかける
2. **既存全体とマージした状態でも検証**: `existing.A.concat(draftA)`のように全難易度をマージし、同じスクリプトにかける
3. **典型的に見つかる問題とその対処**:
   - 難易度またぎの完全重複(並行実行のため、AとBが同じ話題を独立に書いてしまうことがある) → より適切な難易度側に残し、もう一方から削除
   - **同一難易度を複数体で並行作成した場合、相互の重複がかなりの件数(目安2割弱)発生する** → `answer`が一致する組を全て抽出し(完全一致の問題文チェックだけでは大半を見逃す)、それぞれ「同じ事実の言い換えか、たまたま答えが同じ別の事実か」を目視で判定する。後者(例: 答えは同じ「ポルトガル語」だが問うている単語が別)は重複ではないので両方残す。前者は片方を削除する(どちらを残すかは可読性で判断でよく、強いルールはない)。既存バンク全体に対しても同じ`answer`一致チェックをしておくと安心だが、こちらは大半が別事実の偶然の一致で、重複は稀([[project_question_bank_2393]]の2026-10-05の記録を参照)。
   - 表示名が日本語になっていない(例: 誤答の名前が英単語のまま) → 気づいたら手動で日本語に修正
   - 上記いずれも、`scripts/validate-questions.js`は自動検出しない(完全一致の問題文重複は検出するが、言い換えによる重複やどちらを残すべきかの判断は人間/Claude側で行う)
4. 全てクリアになったら`questions.json`に書き込み、`node -c server.js`等で構文確認

## 全体チェック(第三者監査)の観点

問題バンク全体を監査する場合は、次の項目を必ず含める(2026-10-07にユーザーが追加を指示)。

1. **答え漏れ**: 答えそのものだけでなく、言い換え・単位・別名・語源・社名などで答えが当たる問題も対象。削除で対応する(書き換えはしない)。
2. **カタカナ/ひらがなの不一致**: 外来語・外国の人名地名などは、answerとinputの両方でカタカナを保つ(ルール10)。誤答側(distractors)も対象。
3. **難易度の妥当性**: A/B/Cの基準に照らして移動先を提案する。移動は一覧を見てからユーザーが決める。
4. **事実誤り**: 数字・年代・時事はWebSearchで確認。説が分かれるものは断定せず要確認として報告する。
5. **ジャンルの偏り**: 問題バンク全体で、地理・歴史・理科・スポーツ・エンタメ・語学・文学・美術など、ジャンルごとの問題数を集計して偏りがないかを確認する。特定のジャンルに極端に寄っている場合は、偏りの内容と追加すべき方向を報告する。
6. **重複**: 同じ答えの組を事実単位で判定する(同一難易度内は1つに統一、難易度またぎは内容で判定)。

## 手順4: 動作確認

[[live-bot-verify]] の要領で、サーバーを再起動(`questions.json`はrequireでメモリに載るため必須)し、socket.io-clientボットで各難易度数問ずつ実際に出題→早押し→解答まで通す。CPU対戦を無効にし、`game:setWinScore`/`game:setQuestionLimit`を0にしておくと連続で回しやすい。

## 手順5: コミット前確認

このプロジェクトの通例として、内容をユーザーに要約報告し、明示的な承認を得てからコミット・プッシュする(件数、見つかった問題と対処、検証結果を簡潔に)。

## サブエージェントがAPI利用制限で失敗した場合

サブエージェントが「セッション制限に達した」等で`failed`ステータスになっても、**出力ファイルが既に書き出し済みのことがある**。まずファイルの存在と内容を確認し、無ければ制限解除後に`SendMessage`で「検証は済んでいるはずなのでそのまま書き出してください」と再開させる(再度リサーチをやり直させない)。

## 適用範囲

このスキルは hayaoshi-quiz プロジェクト専用。既存問題の品質チェック(重複・答え漏れ等の一括検証)だけを行いたい場合は、新規作成なしに `node scripts/validate-questions.js` を直接実行すればよい([[project_scripts_validate_questions]]参照)。
