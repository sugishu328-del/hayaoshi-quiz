# hayaoshi-quiz 見た目の確認(スクリーンショット)

CSSやレイアウトの変更は、コードを読んだだけでは実際の見た目(余白のバランス、色の相性、要素の重なりなど)が分からない。[[feedback_verify_dont_guess]] の方針をUI変更にも適用し、Playwrightで実際にスマホ幅(375×812)でレンダリングしたスクリーンショットを見てから完了とする。

## 基本手順

1. **ポート3000が空いているか確認**(`Get-NetTCPConnection -LocalPort 3000 -State Listen`)。空いていなければ、既存プロセスは(意図しないものでなければ)そのまま使ってよい。CSSだけの変更ならサーバー再起動は不要(静的ファイルは毎回ディスクから読まれる)。**server.js/room.js/gameData.js/questions.jsonを変更した場合はサーバー再起動が必須**(require結果がプロセス起動時にメモリに載るため)。
2. `npm install --no-save playwright` で一時導入する。
3. 検証スクリプトはプロジェクト直下に `_test_*.js` という名前で置く(後で確実に見分けて削除するため)。
4. 375×812のビューポートで `chromium.launch()` → `page.goto('http://localhost:3000/')` し、確認したい画面まで実際にUI操作で進める(参加→モード選択→難易度設定→早押し→4択、など)。`page.screenshot({ path: '_shot_xxx.png' })` で保存する。
5. `Read` ツールでスクリーンショットのPNGを直接見て確認する(自分の目で見て判断する。ファイルが存在するかだけの確認では不十分)。
6. **必ず後片付けする**: `_test_*.js` と `_shot_*.png` を削除、`npm uninstall playwright`、`git status --short` で意図しない差分が残っていないか確認。

## 「実装前に見てから判断したい」場合(色の比較など)

ユーザーが「まずは見てみたい」「実装するか見てから決めたい」と言った場合、本採用前提で1案だけ作らず、次のように進める:

1. 候補ごとに対象のCSS変数(例: `--color-primary`)を一時的に書き換える → スクリーンショット → 元の値に戻す、を候補の数だけ繰り返す(1つのNode/JSスクリプトの中で `fs.readFileSync` で元の内容を保持しておき、各候補適用→スクリーンショット→最後に必ず元の内容へ書き戻す、という形にすると確実)。
2. 全候補のスクリーンショットを撮り終えたら、`git status --short public/style.css` などで**変更が残っていないこと**を確認してからユーザーに見せる。
3. ユーザーが選んだ案だけを本実装として改めて適用し、再度スクリーンショットで確認してからコミットする(使い捨てスクリプトでの一時適用をそのまま「実装」として扱わない)。

## 実機(スマホ)での最終確認をしたい場合

ローカルのPlaywrightスクリーンショットで大枠を確認した後、ユーザーが自分のスマホで実際に触って確認したいと言うことがある。その場合:

1. パソコンのLAN内IPアドレスを確認する(`ipconfig` のWi-Fiアダプタの IPv4アドレス)。
2. [[reference_line_notify_skill]] を使い、`http://<LAN-IP>:3000` をLINEで送る(送信前に必ずメッセージ内容をユーザーに確認する)。
3. **注意**: `crypto.randomUUID()` はセキュアコンテキスト(https/localhost)でしか使えず、LAN経由のhttpアクセスでは使えない。もしこの関数を新たに使うコードを書いた場合は [[feedback_secure_context_lan_access]] のフォールバックパターンを踏襲する。

## よくある落とし穴

- タイプライター演出中の問題文をDOMから読み取ろうとすると、表示途中の一部だけしか取得できないことがある(全部読み終わるまで待つか、早押し直後の途中状態を前提にしたテストにする)。
- CPU対戦を有効にすると、UI操作なしに早押し・正解/不正解が自動で進むため、「早押し後のポップアップ」「不正解演出」等を見るテストが書きやすい(自分で正解を選ぶロジックを組まなくてよい)。
- デフォルトの5点先取設定だと短いテストで`gameOver`になってしまうことがある。複数ラウンドを見たい場合は`game:setWinScore`/`game:setQuestionLimit`を0(無制限)にする。
- **`<input type="file">`のアップロードUIをテストする場合**、対象の`<input>`にいきなり`page.setInputFiles()`するだけでは、その入力を開くはずだったボタン側のクリックハンドラ内で設定される状態(例: 「どのコールバックに結果を渡すか」を覚えておく変数)がセットされないまま終わり、見かけ上は成功したように見えて実際は何も反映されない、ということが起きる(2026-09-01、アイコン画像アップロード機能で実際に踏んだ)。**必ず先に実際のUI操作(アップロードボタンのクリック等)を行ってから**、`page.setInputFiles()`でファイルを渡すこと(ボタン側の`input.click()`はPlaywrightがネイティブダイアログとして横取りするだけで、その前に実行されるべきJSの副作用は普通に実行される)。

## 適用範囲

このスキルは hayaoshi-quiz プロジェクト専用。サーバー側ロジック(タイマー・状態遷移など)の検証には代わりに [[live-bot-verify]] を使う(socket.io-clientで直接イベントをやり取りする方が確実で速い)。見た目と実際の音声再生を両方確認したい場合は、音声側は [[feedback_audio_verification_technique]] のAudioContext計装パターンを併用する。
